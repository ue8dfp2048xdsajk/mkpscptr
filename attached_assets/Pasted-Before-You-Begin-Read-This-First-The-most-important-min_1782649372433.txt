Before You Begin — Read This First
The most important mindset shift for a first-time builder:
Every phase will take 2-3× longer than you expect. That's normal. The goal at each stage is a working thing, not a perfect thing. Ship it, then improve it.
Accounts to create before writing a single line of code:
1. GitHub — create a free account, create a private repository, push your existing app to it. This is your version history and your deployment source. If you break something, you can always go back.
https://github.com/ue8dfp2048xdsajk/mkpscptr
2. Vercel — connect to your GitHub account. Every push to GitHub auto-deploys. Takes 10 minutes.
https://mkpscptr.vercel.app/
3. MongoDB Atlas — create a free cluster. Note down the connection string.
4. Clerk — create an application. Note down your publishable key and secret key.
5. Stripe — create an account. Keep it in test mode until you're ready to go live.
6. Resend — create an account, verify your sending domain.
7. PostHog — create a project, grab the JS snippet.
Environment variables — understand this before day one:
Every secret (API keys, database passwords) lives in a .env file locally and in Vercel's dashboard online. They are never committed to GitHub. This is how you keep secrets out of public code. Vercel has a "Environment Variables" section in every project — this is where you paste them for production.
Never build two things at once. Finish one phase completely, test it works, then move on. First-timers get into trouble by building half of auth, half of Stripe, and half of the database at the same time — nothing works and you can't tell why.

Phase 0 — Foundation
Estimated time: 2–3 days
What you're doing:
• Push existing app to GitHub
• Deploy to Vercel — get it live at a real URL
• Add PostHog analytics snippet to index.html
• Add mobile detection overlay
• Add schemaVersion: 1 to your project JSON serialisation
What to be aware of:
• Vercel will ask you to configure your project. Since it's a plain static site with no build step, set "Framework Preset" to Other and "Output Directory" to . (the root). If Vercel tries to run npm build it'll fail — tell it not to.
• Buy your domain now (e.g. mockupscripter.com on Namecheap or Cloudflare). Connect it to Vercel via DNS settings. Vercel has step-by-step instructions. This takes 24-48 hours to propagate.
• PostHog integration: copy their JS snippet into <head> of index.html. That's it — events fire from day one.
Done when: Your existing app is live at your real domain, analytics are recording visits.

Phase 1 — Watermark System
Estimated time: 3–5 days
What you're doing:
• Add a Fabric.js overlay object (watermark) that appears on every canvas window when a design is uploaded
• Watermark must survive all transforms and not be exported
• Add the "Remove watermarks — upgrade" pulse prompt in the top bar
• Add ⭐ PRO badges to left sidebar sections
• Add ⭐ star badge to canvas wrapper when a PRO feature is applied
• Track which windows have PRO effects applied (hasProEffect: true per window in your data model)
What to be aware of:
• Do this phase entirely in the frontend before touching any backend. The watermark logic lives in app.js — no server needed.
• The watermark object needs excludeFromExport: false (it should render in exports for free users) but evented: false (can't be clicked or selected). It should be the topmost Fabric object on the canvas.
• Serialize hasProEffect into your JSON alongside all other window state. Test saving and restoring it.
• This phase is the business-critical part of your app. Test it thoroughly: can a user remove the watermark via browser dev tools? (They will try.) The watermark should be re-applied on every render, not just once.
Done when: Designs upload → watermark appears → watermark survives all transforms → PRO features badge correctly → exporting a watermarked canvas produces a watermarked image.

Phase 2 — Auth with Clerk
Estimated time: 3–5 days (longer for a first-timer)
What you're doing:
• Install Clerk's browser SDK
• Add Login / Sign Up to your top bar (Clerk provides pre-built UI components)
• Create a /login and /signup page (or use Clerk's hosted pages — easier)
• Wire Forgot Password (Clerk handles it automatically)
• Wire the welcome email trigger (Clerk has a webhook that fires on user creation)
• On sign-in: show account avatar in top bar, Dashboard link, Log Out
What to be aware of:
• Clerk's "hosted pages" option means you don't build any login UI yourself — users are redirected to accounts.yourdomain.com which Clerk controls. This is the fastest path. Only build custom UI if the hosted pages feel wrong visually.
• Every Vercel API route that requires a logged-in user should verify the Clerk session token. Clerk provides a getAuth() helper for this. If you forget this on any route, it's a security hole.
• "Remember where the user was going" — when the export gate redirects to login, you need to store the destination (e.g. Plans page + their chosen plan) in sessionStorage before redirecting, then read it after auth completes. This is a common gotcha for first-timers: auth redirects back to the homepage and the user loses context.
Done when: User can sign up with Google or email, log in, log out, reset password, see their avatar in the top bar.

Phase 3 — MongoDB + Project Save/Load
Estimated time: 4–6 days (database work is the biggest learning curve)
What you're doing:
• Create a Vercel API route: POST /api/projects/save — receives JSON, saves to MongoDB, returns UUID
• Create a Vercel API route: GET /api/projects/[id] — returns project JSON by UUID
• Anonymous saves (pre-login): rate limited by IP (1 per 10 min, 15MB max), 48-hour TTL
• Authenticated saves: linked to Clerk user ID, no TTL for paid/free limits
• After login: claim the anonymous UUID and link it to the user's account
• Auto-save in app.js (debounced 30 seconds) to call your save API
• schemaVersion: 1 checked on every load — migration function stub ready
What to be aware of:
• MongoDB connection caching on Vercel is the #1 gotcha for serverless + MongoDB. Every cold start creates a new connection. Without caching, you'll hit Atlas's connection limit fast. The fix is one file — a connection utility that checks if a connection already exists before creating a new one. Search "MongoDB Vercel serverless connection" — copy the exact pattern.
• Keep your MongoDB schema simple: one projects collection ({ uuid, userId, data, schemaVersion, createdAt, updatedAt, expiresAt }), one users collection ({ clerkId, plan, planPeriod, stripeCustomerId, projectCount }). Don't over-engineer the schema on day one.
• Test anonymous save → login → claim UUID flow manually before wiring it up properly. It's the trickiest user journey.
• 15MB JSON size limit: MongoDB has a 16MB document limit. Your 15MB project cap keeps you safely under it.
Done when: Projects save and load correctly for both anonymous and logged-in users. Auto-save fires every 30 seconds without breaking anything.

Phase 4 — Plans Page + Stripe
Estimated time: 5–7 days (most complex phase)
What you're doing:
• Build the Plans page (FREE / STARTER / PRO, monthly/annual/lifetime tabs)
• Create Stripe Products and Prices in the Stripe dashboard (6 prices: Starter monthly, Starter annual, Starter lifetime, Pro monthly, Pro annual, Pro lifetime)
• Create a Vercel API route: POST /api/checkout — creates a Stripe Checkout Session for the chosen plan, returns the checkout URL
• Redirect user to Stripe's hosted checkout page
• Create a Vercel API route: POST /api/webhooks/stripe — handles checkout.session.completed, customer.subscription.updated, customer.subscription.deleted, invoice.payment_failed
• On successful payment: update user's plan in MongoDB, send receipt via Resend
• Stripe webhook signature verification: stripe.webhooks.constructEvent(rawBody, sig, secret) — do not skip this
What to be aware of:
• Test mode first, always. Stripe has test card numbers (4242 4242 4242 4242) — use them. Do not switch to live mode until every flow works perfectly in test mode.
• Raw body on the webhook route — add export const config = { api: { bodyParser: false } } at the top of your webhook API file. Without this Vercel parses the body and Stripe's signature check fails.
• Idempotency — your webhook handler must check if you've already processed an event before acting on it. Store processed Stripe event IDs in MongoDB (processedEvents collection with TTL). Without this, a retry from Stripe could double-upgrade someone.
• The Plans page is just HTML and CSS — build it as a static page first with hardcoded prices, then wire up the checkout API call. Don't try to do both at once.
• Lifetime plans in Stripe are one-time payments (payment_intent), not subscriptions. Handle the payment_intent.succeeded webhook separately from customer.subscription.*.
Done when: Test user can pick a plan, go through Stripe checkout with test card, land on Dashboard with correct plan badge, and your MongoDB correctly reflects their plan.

Phase 5 — Email with Resend
*Estimated time: 2–3 days
What you're doing:
• Create email templates for each trigger in your email sequence (plain HTML emails are fine to start)
• Wire Resend SDK calls into the appropriate API routes (after successful payment, after account deletion, etc.)
• Set up Resend with your domain's DNS records (SPF, DKIM) for deliverability
What to be aware of:
• DNS records for email take 24-48 hours to propagate. Set them up at the start of this phase.
• Start with the 4 most critical emails: welcome, payment receipt, password reset (Clerk handles this one), payment failed. Add the rest after.
• Plain HTML emails with inline CSS only — no external stylesheets, no JavaScript. Email clients are from the 1990s.
• Send yourself a test email for every template before wiring it to real triggers. Check it in Gmail, Apple Mail, and on mobile.
Done when: User signs up → gets welcome email. User pays → gets receipt. Card fails → gets alert email.

Phase 6 — Dashboard
Estimated time: 4–6 days
What you're doing:
• Build /dashboard page: project grid, rename, delete, + New Project
• Build project thumbnail generation (render canvas to a small image at save time, store as base64 in MongoDB)
• Mockup counter (sum of all windows across all projects)
• Plan badge + Upgrade link for Free/Starter users
• Wire "click project → open app with state restored"
What to be aware of:
• Thumbnail generation: at save time, render the first canvas window to a small (300×200) JPEG and store it alongside the JSON. Don't try to generate thumbnails at display time — it's too slow.
• "Open project" means: navigate to the app URL with a ?projectId=UUID query param, read the param on load, fetch the project JSON, restore state. Test this flow carefully — it's where JSON schema migration logic first becomes real.
• Keep the dashboard simple. A grid of cards with name, thumbnail, last-edited date, and a delete button is enough for v1. Don't over-design it.
Done when: User can see all their projects, rename them, delete them, and reopen them in the app exactly as they left them.

Phase 7 — In-App Plan Enforcement
Estimated time: 3–4 days
What you're doing:
• On app load (when user is logged in): fetch their plan from your API, store it in a JS variable
• Apply plan rules: watermark logic, PRO feature gating, export blocking
• Export flow: if not logged in → redirect to Plans page. If logged in Free → redirect to Plans page. If Starter exporting ⭐ starred window → inline prompt.
• Subscription lifecycle: upgrade/downgrade/cancel buttons in Settings trigger Stripe Customer Portal (Stripe's hosted billing management page — use this instead of building your own)
What to be aware of:
• Stripe Customer Portal is the fastest way to handle upgrade/downgrade/cancel. One API call creates a portal session, user is redirected to Stripe's hosted page where they manage their subscription. You get webhooks when things change. Do not build your own billing UI — use the portal.
• Plan enforcement in the frontend is for UX only — it is not security. A determined user can bypass client-side JS. This is fine: the only things that truly need server-side enforcement are export (which requires your API to generate/process) and project saves (which check plan on the server). Watermarks and ⭐ stars are UX gates, not security gates.
• The discount prompt (20% off before downgrade/cancel) is done via Stripe Customer Portal's configured retention flows — set this up in the Stripe dashboard under "Customer Portal settings". No code needed.
Done when: Free user can't export without watermark. Starter user can't export ⭐ starred windows. Pro user has no restrictions. All subscription changes work via Stripe portal and update MongoDB via webhook.

Phase 8 — Settings, Legal, Polish
Estimated time: 3–4 days
What you're doing:
• Build /settings page (Personal, Plan & Billing, Payments, Support)
• Account deletion: Clerk deleteUser() + MongoDB cleanup + confirmation email
• Invoice history: pull from Stripe API (stripe.invoices.list({customer: customerId}))
• Write Privacy Policy and Terms of Service (use a generator like Termly or Iubenda for a first draft — don't write from scratch)
• Add cookie consent banner (trigger PostHog initialisation only after accept)
• Mobile detection overlay
• 404 page
What to be aware of:
• Privacy Policy and Terms of Service are legal documents. Use Termly or Iubenda to generate them — they know what's legally required. Customise the outputs for your specific refund policy and data handling.
• Account deletion must delete from both Clerk AND MongoDB. Don't leave orphaned data in either place.
• The cookie consent banner must fire before PostHog loads — PostHog supports a "delay initialisation" pattern for exactly this.
Done when: All settings work, legal pages are live and linked, mobile users see the overlay.

Phase 9 — Testing & Launch
Estimated time: 5–7 days
What you're doing:
• Full end-to-end test of every user journey in the plan document (do this yourself, manually)
• Switch Stripe to live mode, update environment variables in Vercel
• Make a real purchase with your own card to verify the entire payment flow
• Set up Stripe's webhook in live mode (separate from test mode webhook)
• Soft launch to your own traffic source
What to be aware of:
• Test every branch in the plan document manually, in order. Export gate → Free branch. Export gate → Starter branch. Export gate → Pro branch. Returning user. Downgrade flow. Lapse flow. Don't assume something works because the test mode worked — test live mode with a real card.
• Stripe live mode needs a separate webhook endpoint configured in the Stripe dashboard. Copy the same route URL, update the webhook signing secret in Vercel's environment variables.
• Keep test mode webhooks active alongside live — you'll want to keep testing without spending real money.
• Do not launch until you've personally gone through checkout with a real card, got the receipt, saw the plan update in MongoDB, and successfully exported a watermark-free mockup.
Done when: Everything works end to end in live mode. You've made a real test purchase. You're live.

An experienced developer would do this in 3–4 weeks. As a first-time builder using AI assistance throughout, 8–12 weeks is realistic and nothing to be discouraged by — the app itself is already built, which is the hardest part. Everything from here is plumbing.

The One Rule to Follow Throughout
When something breaks and you don't know why: read the error message out loud, then search it exactly. 95% of the errors you'll hit have been hit by thousands of developers before you and are answered on Stack Overflow or in official documentation. The remaining 5% are things to bring here. Never spend more than 20 minutes stuck on something before asking for help.
